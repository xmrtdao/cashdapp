### Critical bug found during testing

The markdown function was placed inside the big `res.send(\`<!DOCTYPE html>` template literal that starts at line 1388. The function's `//` comment contained literal backticks (`` // Supports: \`code\`, \`\`\`code blocks\`\`\` ``), and the regex literals used backticks. V8's parser doesn't recognize `//` comments as comments when it's inside an open template literal — backticks there flip it into template-literal-parsing mode, which then derails the entire parse. V8 errored at line 2093 (the next `const SUPABASE_URL = '${...}'`), making the bug look unrelated to my code.

Fix: replaced all literal backticks in the function's regexes with `\x60` hex escapes (`\x60` = `` ` ``). The regex engine still sees the real character at runtime, but the source code has no literal backticks anywhere in the open template literal. Also rewrote the `//` comment to use `[apostrophe]code[apostrophe]` style instead of backticks.

Tested the renderer in isolation: all 3 test cases (formatted post, XSS attempt, mixed formatting) produce correct sanitized HTML. Relay restarted (PID 2164), health green, no parse errors. Articles post on the board will now render with proper headings, tables, lists, and bold text.

### General lesson
**Never put a function definition (or any code with backticks) inside a giant `res.send(\`...\`)` HTML template literal.** Move helpers to a separate file or define them before the route handler. The template-literal context changes how `//` comments parse, and V8 won't tell you where the real problem is — it'll fail at the next `const FOO = '${...}'` and you'll spend 30 minutes chasing the wrong line.

### CI Build Saga (Flutter 3.44 v1 Embedding Check)

The CI build of `xmrt-node` was failing with:
  Build failed due to use of deleted Android v1 embedding.

This error has been silently blocking every push to main since
2026-05-28. Tracked it down to a real Flutter 3.44 regression.

**The check (in flutter_tools/lib/src/project.dart:956):**
- `AndroidProject.checkForDeprecation` runs as a pre-build sanity
- It calls `computeEmbeddingVersion()` which parses
  `android/app/src/main/AndroidManifest.xml`
- Looks for `<meta-data android:name="flutterEmbedding" android:value="2"/>`
  inside `<application>` to return v2
- If not found, returns v1 and throws

**The misdirection:**
- I initially thought the error was from a plugin (file_picker,
  flutter_tts) referencing v1 embedding classes
- Pinned both plugins to specific versions, no effect
- Re-ran with `--verbose`, got the stack trace pointing to the
  pre-build check (NOT gradle output)
- Added the missing `<meta-data android:name="flutterEmbedding"
  android:value="2"/>` to the manifest
- The build STILL failed

**Confirmed (CI dump via python + dart):**
- `python3` parses the manifest correctly, finds:
    application android:name = ${applicationName}
    meta-data android:name = flutterEmbedding  android:value = 2
- Yet Flutter's `computeEmbeddingVersion` returns v1
- Stack trace: `AndroidProject.checkForDeprecation (project.dart:956:5)`
  -> `throwToolExit('Build failed due to use of deleted Android v1
  embedding.', exitCode: 1)`
- The `result.reason` (e.g. "No meta-data with value 2") is NOT
  printed by `checkForDeprecation`, so we can't see which branch
  is hitting

**My best guess (unverified):** Flutter 3.44 uses `package:xml 6.6.1`
and the new `computeEmbeddingVersion` has a bug where the
`application/android:name="${applicationName}"` placeholder
resolves weirdly, OR the meta-data `findAllElements` is recursive
in a way that misses direct children of <application>.

**Fix shipped (commit 50346a0):**
- Kept the `flutterEmbedding=2` meta-data in the manifest
- Kept the `tools:` namespace
- Removed speculative `flutter_tts 4.2.2` / `file_picker 8.3.7` pin
  (not the cause, just a guess)
- Restored the `package="io.xmrt.node"` attribute on <manifest>
- Simplified the build step to use `set -eo pipefail` + test on
  `${PIPESTATUS[0]}` so the workflow correctly reports failures
  (previously `tail -200` masked the build exit code)

**Tracking issue:** This is a Flutter SDK bug, not an xmrt-node
bug. Should file against flutter/flutter. Until then, options for
the project:
1. Pin Flutter to 3.26.x (before v1 check was added) in the
   workflow
2. Skip the build verification and rely on manual testing
3. Use `flutter build bundle` (no pre-build check) to verify
   compile but skip the APK
4. Wait for Flutter SDK fix
