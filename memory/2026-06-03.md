# 2026-06-03 — Wednesday Session

## System Health Sweep + Critical Cron Regression Fix — 10:30 CST

Joe asked: "ensure systems are operational". Did a full sweep and
discovered the cron task dispatcher has been silently 404-ing for
**2 days straight** (46 cumulative errors, escalating from 1-2/hour
in May to 7/hour by 2026-06-02).

### Root cause

Commit `7e70bac` ("feat: add missing mesh dashboard endpoints")
on 2026-06-01 14:41 (mine) added mesh endpoints but accidentally
clobbered a chunk of POST route handlers. The banner URL line
`http://0.0.0.0:8080/webhook/task` survived, so cron kept POSTing
to a 404.

**Routes deleted in 7e70bac, restored this session:**
- `/webhook/task` — main task dispatcher (the big one)
- `/webhook/task/result` — Hermes result callback
- `/eliza-ping` — Eliza-Cloud ping-pong
- `/dispatch` — generic keyword/structured dispatch
- `/eliza/send` — HTTP wrapper around relayToElizaCloud
- `/log` — remote activity logging
- `/webhook/resend-inbound` — Resend inbound email webhook
- `/log/sent` — sent email logging
- `logSentEmail()` helper that /log/sent depends on

### How I found it

1. Ran cron `--once` — clean run, 0 errors this cycle, BUT the
   cumulative counter was 46 errors (up from 5 yesterday)
2. State file at `C:/Users/PureTrek/Desktop/relay-data/cron-state.json`
   (NOT in the repo, one dir up — easy to miss)
3. Errors had a clear escalation:
   - 2026-05-18 to 2026-05-30: 1 error/hour (initial state, with
     a few historical errors before the routes went missing)
   - 2026-06-02 21:10 onward: 7 errors/hour
   - 2026-06-03 05:10: 3 errors/hour (last seen before fix)
4. `git log -S "app.post('/webhook/task'"` showed the handler
   was deleted in 7e70bac (Jun 1) — my own commit
5. Banner URL line was still in the file -> cron kept trying

### Lesson learned

**The `state.errors` array in `cron-fetch-tasks.mjs` is the canary
for "POST routes that the cron thinks exist but actually don't."
Errors only count when there's a task to dispatch — if 0 pending,
0 errors. So the failure was silent for hours at a time.

The state file lives at `C:/Users/PureTrek/Desktop/relay-data/cron-state.json`
(one directory above the repo) — easy to miss. Should consider
moving it into `relay-data/` or a `state/` dir for visibility.

Also: the `// API: ...` comment convention I use makes route
sections easy to find, but doesn't help me notice when a route
goes missing. Consider adding a route inventory file that gets
regenerated by grepping `app.post`/`app.get` declarations, then
diffed on every commit to catch regressions like this one.
