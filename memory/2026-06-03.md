## System Health Sweep + Critical Cron Regression Fix — 10:30 CST

Joe asked: "ensure systems are operational". Did a full sweep and
discovered the cron task dispatcher has been silently 404-ing for
**2 days straight** (46 cumulative errors, escalating from 1-2/hour
in May to 7/hour by 2026-06-02).

### Root cause

Commit `7e70bac` ("feat: add missing mesh dashboard endpoints")
on 2026-06-01 14:41 (mine) added mesh endpoints but accidentally
clobbered a chunk of POST route handlers. The banner URL line
`http://0.0.0.0:8080/webhook/task` survived, so cron kept POSTing
to a 404.

**Routes deleted in 7e70bac, restored this session:**
- `/webhook/task` — main task dispatcher (the big one)
- `/webhook/task/result` — Hermes result callback
- `/eliza-ping` — Eliza-Cloud ping-pong
- `/dispatch` — generic keyword/structured dispatch
- `/eliza/send` — HTTP wrapper around relayToElizaCloud
- `/log` — remote activity logging
- `/webhook/resend-inbound` — Resend inbound email webhook
- `/log/sent` — sent email logging
- `logSentEmail()` helper that /log/sent depends on

### How I found it

1. Ran cron `--once` — clean run, 0 errors this cycle, BUT the
   cumulative counter was 46 errors (up from 5 yesterday)
2. State file at `C:/Users/PureTrek/Desktop/relay-data/cron-state.json`
   (NOT in the repo, one dir up — easy to miss)
3. Errors had a clear escalation:
   - 2026-05-18 to 2026-05-30: 1 error/hour (initial state, with

4. `git log -S "app.post('/webhook/task'"` showed the handler
   was deleted in 7e70bac (Jun 1) — my own commit
5. Banner URL line was still in the file -> cron kept trying

### Lesson learned

**The `state.errors` array in `cron-fetch-tasks.mjs` is the canary
for "POST routes that the cron thinks exist but actually don't."
Errors only count when there's a task to dispatch — if 0 pending,
0 errors. So the failure was silent for hours at a time.

The state file lives at `C:/Users/PureTrek/Desktop/relay-data/cron-state.json`
(one directory above the repo) — easy to miss. Should consider
moving it into `relay-data/` or a `state/` dir for visibility.

Also: the `// API: ...` comment convention I use makes route
sections easy to find, but doesn't help me notice when a route
goes missing. Consider adding a route inventory file that gets
regenerated by grepping `app.post`/`app.get` declarations, then
diffed on every commit to catch regressions like this one.

## Tunnel DNS Routing Fix — 11:33 CST

Joe asked: "check that relays tunnels and node services are up".
Full sweep found:

### What was broken
- `relay.mobilemonero.com` was resolving to Cloudflare's generic
  worker IPs (104.21.17.92, 172.67.175.106) — NOT my tunnel
- A Worker route `relay.mobilemonero.com/* -> api-gateway` was
  intercepting all traffic and returning `{"ok":true,"worker":"api-gateway"}`
  for /health and 404s for webhook paths
- A stale A record `relay.mobilemonero.com -> 184.170.245.6` was
  shadowing what should have been a CNAME to the tunnel
- This is **why cron has been getting 46 errors** for 2 days —
  POST /webhook/task hits the worker, gets 404
- The named tunnel process was NOT running (no cloudflared PID)

### What I fixed
1. Killed nothing, started cloudflared with existing config:
   `5d954e14-ea46-48e4-bc50-9c3a2be1760c` -> localhost:8080.
   Got 3 healthy connections (sjo01 + 2x mia08).
2. Deleted stale A record via CF API:
   `cb3f37ba4a255972542b4a0f865ea549` (DELETE -> success)
3. Added CNAME to tunnel via CF API:
   `relay.mobilemonero.com -> 5d954e14...cfargotunnel.com`
   (proxied=true, new id `8290b25932b50906d7767bd5fbf5645a`)
4. Removed Worker route that was blocking:
   `relay.mobilemonero.com/* -> api-gateway`
   (id `46002dd292204bd3a1d0d63e633a61fb`, DELETE -> success)
5. Re-ran `start-tunnel.mjs --update-only` to re-point Resend
   PFP webhook to the now-functional URL. PFP webhook updated
   cleanly. XMRT webhook still fails (the hardcoded Resend
   webhook ID `f3546199-...` is gone — same blocker as
   yesterday's open issue).

### Lesson learned
**The relay, tunnel config, and CF DNS/Worker routes are
three independent things that all have to be aligned.** When
webhooks 404, don't just check the relay — check (1) is
cloudflared running, (2) is the DNS record a CNAME to the
tunnel, (3) is there a Worker route shadowing the domain.
Yesterday I fixed the relay; today I had to fix DNS + Worker.

The `state.errors` array in cron is the canary for
misrouted webhooks — the 46 errors were the only signal that
the routing was broken for 2 days. Should add a daily
heartbeat test: `curl https://relay.mobilemonero.com/health`
and verify the JSON body matches what `localhost:8080/health`
returns. If the bodies differ, the tunnel is being shadowed.
