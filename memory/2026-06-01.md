## Cmd-Popup Fix (cmd.exe flashing every 5 min, 2-3 in a row)

**Root cause:** XMRT-Relay-Watchdog ran every 5 min, and its auto-restart path used `spawn('node', ...)` (no `windowsHide: true`) which opens a visible console on Windows. Plus the task itself wasn't `Hidden`. Plus `RestartOnFailure` was set to Count=3, so when one run failed the scheduler retried twice more = 2-3 in a row.

**Fix applied:**
1. `relay/relay-watchdog.mjs` -- replaced `execSync('taskkill ... 2>nul || true')` (uses shell, pops cmd) with `execSync('taskkill.exe', [...], { windowsHide: true })` wrapped in try/catch.
2. `relay/relay-watchdog.mjs` -- replaced `spawn('node', ['relay/server.js'], { detached: true })` with `spawn(process.execPath, [...], { detached: true, windowsHide: true })`.
3. Re-registered all 7 XMRT tasks via PowerShell `Register-ScheduledTask -Hidden` (schtasks /XML with `<Hidden>` causes a known "null reference pointer" COM crash on this build -- PS module is the working path).
4. Capped watchdog `RestartOnFailure` Count=2 (was 3), interval PT5M.
5. All schedules moved to Costa Rica timezone (-06:00) StartBoundary.

**Result:** 6/7 tasks now Hidden=True. The 7th (`XMRT-DAO-HourlyTaskFetch`, original from 2026-05-11) has a locked security descriptor (only Administrators/SYSTEM have full control, current user has only FR). Needs an **admin PowerShell** one-liner to clean up -- provided to Joe. It's harmless (v2 does the same hourly work hidden) but will flash a brief console if it ever fires.

## YellowKey (CVE-2026-45585) Audit — 22:55 UTC

**What it is:** BitLocker bypass via USB. Attacker with physical access drops FsTx files on a USB stick, boots target into WinRE, holds CTRL -> shell spawns on the encrypted volume. CVSS 6.8. Public PoC by Nightmare-Eclipse (a.k.a. Chaotic Eclipse), dropped without coordinated disclosure on 2026-05-12. Microsoft issued mitigation guidance 2026-05-20, no patch yet.

**Affected systems:** Windows 11 24H2 / 25H2 / 26H1 (x64), Windows Server 2025 (+Core), and possibly Server 2022 in some deployments. **Windows 10 NOT affected.**

**This machine:**
- Windows 10 Pro build 18363 (Win10) -> **not in the affected list**
- `manage-bde -status C:` shows **no BitLocker volume** (not encrypted) -> bypass is moot anyway
- Verdict: **Not vulnerable.** Nothing to patch on this box.

**Mitigation steps Microsoft recommends (for affected machines):**
1. `reagentc /info` to locate WinRE.wim
2. `dism /mount-image /imagefile:C:\Windows\System32\Recovery\Winre.wim /index:1 /mountdir:C:\winremount`
3. `reg load HKLM\winRE_SYSTEM C:\winremount\Windows\System32\config\SYSTEM`
4. Edit `HKLM\winRE_SYSTEM\ControlSet001\Control\Session Manager\BootExecute` -> remove the `autofstx.exe` line
5. `reg unload HKLM\winRE_SYSTEM`
6. `dism /unmount-image /mountdir:C:\winremount /commit`
7. `reagentc /disable && reagentc /enable` to re-seal BitLocker trust
8. (Recommended) Switch TPM-only -> TPM+PIN: `Manage-bde -protectors -add C: -TPMAndPIN`

**A scripted helper exists:** `github.com/bjbakker1984/Yellowkey-mitigation` (PowerShell) automates the workflow with verification, skips commit if no change was needed, and re-checks BootExecute. Useful template if we ever need to patch a Win11 box.

**If we ever ship a Win11 laptop in the field (XMRT Charger demo units, contractor loaners, etc.):** those WILL be vulnerable by default. We should:
- Pre-apply the WinRE autofstx.exe removal to all Win11 loaner/demo units before they leave the building
- Set TPM+PIN as the default policy on any Win11 PFP hardware we hand out
- Document this in TOOLS.md under a "Win11 hardening" section so it's not forgotten

**Action item for TOOLS.md:** add a "Windows 11 hardening — YellowKey" section with the dism/reg/reagentc one-liners so any future Win11 setup includes the mitigation by default. Not urgent (no Win11 hardware in fleet), but worth parking.

**Detection signal to add to /monitor (when we have Win11 endpoints):** Event ID 1001 under "Boot Configuration Data" = WinRE entry. Correlate with USB insertion events containing `System Volume Information\FsTx` directories.

## Dashboard "no content loading" — root caused + fixed (03:50 UTC 2026-06-02)

Joe pinged: "check that the relay is up and find out why there is no content loading on localhost:8080".

### Diagnosis
1. **Relay is up** (PID 2304, uptime ~5min, health 200, 62 tools, 7 handlers, 117 requests)
2. HTML serves 96KB, 20+ cards visible. Many cards stuck on "Loading..." or "checking..."
3. The headline card "XMRT DAO HEALTH" said "Supabase: unavailable" even though /api/dao/health returned good data
4. Ran a Chrome headless screenshot to confirm what Joe was seeing — many cards blank

### Root cause (TWO bugs, both from Hermes's f109cc1 commit)

**Bug 1 — Template-literal escape (the big one)**
`loadGithubActivity()` in server.js had `last.commit.message.split('\n')[0]`. The dashboard HTML is built as a single template literal, so at JS parse time the `\n` becomes a real newline byte in the served HTML. The browser sees:
```
.split('<LF>')[0]
```
That's a multi-line string literal without continuation = SyntaxError. The whole 42KB script fails to parse, so EVERY card's loader function never runs. That's why the UI was stuck.

Fix: use `String.fromCharCode(10)` to get a newline at runtime in the browser. The JS source must round-trip through Node's template-literal escape processing.

**Bug 2 — Wrong data nesting depth**
`loadDaoHealth()` checked `d.health.overall_health` but the `/api/dao/health` endpoint returns `{ health: <system-health>, status: <system-status> }` where each child is the raw Supabase response (which has its own `health`/`status` wrapper). So the real path is `d.health.health.overall_health`. Made the JS tolerant of both nesting depths and added the missing "Health Score" and "Tasks" rows in the card.
