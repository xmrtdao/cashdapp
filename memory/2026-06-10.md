## System-health continuation: rest.mjs upsert fix

User asked to continue the system-health work. Root cause of the lingering `agents.status="error"` in `system-status` edge function output: the cron jobs + fleet health queries that the function runs end up calling `.upsert(...)` on `public.api_key_health` and other tables, and our `routes/rest.mjs` was silently dropping the `on_conflict` / `Prefer: resolution=merge-duplicates` semantics — so the inserts failed with `duplicate key` and propagated up as "error" component status.

### What was wrong
`local-supabase/routes/rest.mjs` POST handler:
- Only checked `?on_conflict=col` URL param, never `Prefer: resolution=merge-duplicates` header (real PostgREST honors both)
- Built `ON CONFLICT (col) DO UPDATE SET ...` SQL correctly when conflict target was supplied
- But `preferResolution === 'merge-duplicates'` *without* `on_conflict` silently fell through to a plain INSERT — no error, just wrong behavior

### What I changed (routes/rest.mjs POST handler)
- Parse `Prefer: resolution=...` header, build `onConflictSql` for both `merge-duplicates` and `ignore-duplicates`
- `merge-duplicates` + `on_conflict` → `ON CONFLICT (...) DO UPDATE SET c=EXCLUDED.c`
- `merge-duplicates` + no `on_conflict` → 400 `PGRST114` (mirrors real PostgREST; never guess the unique column)
- `ignore-duplicates` + `on_conflict` → `ON CONFLICT (...) DO NOTHING`
- `ignore-duplicates` + no `on_conflict` → `ON CONFLICT DO NOTHING`
- Validation: `on_conflict` column names must match `/^[a-zA-Z_][a-zA-Z0-9_]*$/` (already there for other columns; just made sure it applied here too)

### Verification (`local-supabase/tests/upsert.test.mjs` — new, 18 assertions)
- All 7 scenarios pass against live local-sb on :54321
- Plain POST, on_conflict URL, Prefer header, error case, ignore-duplicates, bulk array upsert
- Cleanup: `DROP TABLE upsert_test` so no schema pollution

### Why the supervisor's PID-tracking matters
- The supervisor used to rely entirely on `childPid` to know whether a service was alive.
- When a service is spawned manually (Vite via `npm run dev`, local-sb via `node --watch`), the supervisor's state file still tracks a childPid — but that PID is the *previous* manual start, not the current one.
- The new `pidAlive()` + `reconcileStalePids()` + `healthCheck`-driven design lets the supervisor be honest about state: it nulls dead PIDs but uses the health check (HTTP / process-by-script) to decide whether to spawn. If the port is occupied, the supervisor sees the service as healthy and leaves it alone — regardless of who owns the PID.
- This means the supervisor "owns" services only when it spawned them, and "observes" services started manually. Either way, restart-on-health-fail works.

## Fleet chat anti-hallucination grounding (final)

Joe asked: "ok check fleet chat to be sure the agents are responding truthfully after making real tool calls not hallucinating responses".

### Root cause of the hallucination pattern
Vex/Alice/Eliza's prompt blocks were persona instructions + free text. The LLM was free to invent. It would confidently emit "Pipeline nominal. All systems operational. No anomalies detected" without ever calling a single endpoint. The LLM has no idea what the actual state is — it just sounds like it does.

### Solution (commit e29485d)
1. **New `gatherFleetContext()` helper** at `relay/server.js:4814` — fetches `/health`, `/monitor`, `/ollama/health`, `/api/fleet-chat/messages?limit=5`, `/api/supervisor/status` in parallel with per-endpoint timeouts. Returns a compact JSON fact block.
2. **New `GET /api/supervisor/status` endpoint** reading `relay-data/supervisor-state.json` and exposing per-service `childPid`/`startedAt`/`uptimeSec`/`restartCount`/`lastAlert`.
3. **New `GET /api/fleet-chat/grounded` debug endpoint** returning the raw context block — useful for verifying the agent's source of truth.
4. **Injected the JSON into 4 prompt blocks** with explicit `GROUNDING RULES`:
   - Vex: `temperature: 0.5, max_tokens: 180, timeout: 15s`
   - Alice: `temperature: 0.4, max_tokens: 120, timeout: 12s`
   - Eliza deepseek fallback (when eliza-relay EF returns thin/signoff): `temperature: 0.4, maxTokens: 320, timeout: 28s`
   - Idle heartbeat: `temperature: 0.4, max_tokens: 140, timeout: 15s`
5. **GROUNDING RULES text:** "Reference specific fields only when in the JSON. If asked about something the JSON doesn't cover (emails, leads, money), say 'I don't have that data' — don't make it up. Never claim 'all systems nominal' without matching fields."

### Gotcha: /monitor latency vs fetch timeout
`/monitor` itself takes ~4.2s because it pings supabase+hermes upstream with their own timeouts. My initial 2500ms timeout in `gatherFleetContext` was firing before the data came back, leaving `services.*` and `system.*` as `null`. The LLM then saw "null" everywhere and hallucinated "all down" instead of reporting the actual state. Bumped to 6000ms. Also added `monitorFailed` branch that surfaces `_monitorError` and marks fields `fetch_failed` (not `unknown`) so the LLM can distinguish "we don't know" from "we know we couldn't fetch".
